# LEOptical — Seed Data Strategy

Seed data is hosted in the course repo under `static/seed-data/` and introduced in layers matching module progression.

All CRM seed data (Contacts) is generated by a single Python script (`scripts/generate-seed-data.py`) that produces static CSV files checked into the repo. A small anonymous Apex snippet creates Products, PricebookEntries, and Campaigns. The Python script also generates the Data 360 CSVs (`loyalty.csv`, `ecom_customers.csv`, `ecom_orders.csv`, `ecom_order_items.csv`, `clinic_patients.csv`, `clinic_exams.csv`) from the same source of truth, so emails are guaranteed to match across all files.

## Volume & Record Strategy

**~48,672 CRM Contacts** imported via the browser-based Data Import Wizard. All contacts are associated with a single shared Account called "LEOptical Customers".

> **Why one shared Account?** LEOptical is B2C (individual consumers, not businesses). In a production engagement, you would use Person Accounts. We use a single shared Business Account here because Person Account configuration varies across SDOs and is not relevant to MCA. The Marketing Data Kit ingests Contacts into Individual DMOs regardless of Account structure.

All records use `@example.com` emails (IETF-reserved per RFC 2606 — nothing delivers). Email pattern: `firstname.lastname.NNNNNN@example.com` where `NNNNNN` is a zero-padded sequential counter.

### 10 Protagonist Contacts

10 contacts included in `contacts.csv` with `@example.com` placeholder emails. These are pre-configured across loyalty tiers and purchase histories so the learner can test personalization for different scenarios.

In Module 5, the learner runs anonymous Apex to update the 10 protagonist emails to their own address using `+alias` patterns (e.g., `learner+mariac@gmail.com`). Data 360's CRM data stream uses Upsert mode, so the original `@example.com` Contact Point Email record is preserved alongside the new one. This means ecommerce orders (which reference the `@example.com` email) remain linked via IDR, while the learner can receive test emails at their real address.

## Module 1 — CRM Seed Data

### Step 1: Import Contacts via Data Import Wizard

Download `contacts.csv` from course resources. Import using the browser-based Data Import Wizard (**Setup > Data Import Wizard**):

- Select **Accounts and Contacts** under Standard Objects
- Select **Add new records**
- Set **Match Account by** to **Account Name & Site** (ensures one shared Account)
- Upload `contacts.csv`
- Verify field mappings (standard fields and custom fields should auto-map by label)
- Start the import

The wizard creates one Account named "LEOptical Customers" and links all ~48,672 contacts to it.

### Step 3: Create Products and Campaigns (anonymous Apex)

Run `seed-products-campaigns.apex` in Developer Console > Execute Anonymous. Creates 5 Products (with PricebookEntries) and 3 Campaigns.

### Step 4: Verify the data

- ~48,682 Contacts (48,672 + ~10 protagonist contacts + a few intentional duplicates)
- 1 Account named "LEOptical Customers"
- 5 Products
- 3 Campaigns
- Maria Chen exists with Loyalty Tier = Gold
- Wei Zhang exists with Loyalty Tier = Platinum

## Module 5 — Update Protagonist Emails

The learner runs anonymous Apex to update the 10 protagonist contacts' Email field to their own `+alias` addresses. The `SeedScript` component on the page generates this Apex dynamically based on the email address the learner enters.

After the update, Data 360's CRM data stream refreshes and creates a second Contact Point Email for each protagonist. The original `@example.com` email remains, preserving links to ecommerce orders and loyalty records.

## Email Consistency Across Files

The Python script maintains a master registry of all generated people. When a person appears in multiple files (CRM contact + loyalty member + ecommerce customer + exam patient), the script controls exactly which email each file uses. This is how the dirty data scenarios are created deterministically:

- **Same person, same email everywhere:** The common case (~70%). IDR matches these trivially.
- **Same person, different emails:** ~15% of cross-file people use a variant email (e.g., `m.chen@example.com` vs `maria.chen@example.com`). Tests fuzzy matching and multi-email IDR.
- **Same person, typo email:** ~2% have a one-character typo in one source. Tests whether IDR catches near-misses.
- **Different people, same email:** ~50 cases of shared household emails (e.g., `thekims@example.com`). Tests false positive detection.
- **Person in only one source:** ~20% of each file's records have no match in any other file. Tests that IDR doesn't over-merge.

## Dirty Data Strategy

The seed data intentionally includes realistic data quality problems. These are NOT called out to the learner upfront — they discover them as they work through modules, just like on a real engagement.

### Category 1: Identity & Matching Problems (surfaces in Module 7 — IDR)

| Problem | How It Appears | Real-World Parallel |
|---------|---------------|---------------------|
| Different emails, same person | CRM has `maria.chen@work.example.com`, `loyalty.csv` has `m.chen@personal.example.com`, `ecom_customers.csv` has `maria.chen@other.example.com` | Every multi-source client |
| Same email, different people | Two different loyalty members share a family email (`thekims@example.com`) | Shared household emails — common in B2C |
| Name variations | "James Okafor" in CRM, "Jim Okafor" in `loyalty.csv`, "J. Okafor" in `ecom_customers.csv` | Nickname/abbreviation mismatches |
| Typos in email | `sofia.reyez@example.com` vs `sofia.reyes@example.com` — one character off | Data entry errors |
| Duplicate CRM records | 2-3 Contacts that are clearly the same person created twice (same name, slightly different data) | CRM hygiene issues every client has |
| Case inconsistency | `John.Smith@Example.com` vs `john.smith@example.com` | Systems that don't normalize case |
| Multiple emails per person | Protagonist contacts have both @example.com and learner's +alias email after Module 5 update | Real customers have work + personal emails |

### Category 2: Data Quality Problems (surfaces in Modules 6-8 — Data Model & Graphs)

| Problem | How It Appears | Real-World Parallel |
|---------|---------------|---------------------|
| Missing required fields | ~5% of `loyalty.csv` records have no email address. ~5% of contacts have no last name | Incomplete data from legacy systems |
| Inconsistent date formats | CRM dates are `YYYY-MM-DD`, `ecom_orders.csv` has `MM/DD/YYYY`, `loyalty.csv` has `DD-Mon-YYYY` | Every CSV import ever |
| Stale data | ~500 loyalty members with tier "Gold" in `loyalty.csv` but points below the Gold threshold | Snapshot vs. real-time data lag |
| Orphaned records | `ecom_order_items.csv` referencing product SKUs that don't exist in the Product table | System migrations, retired products |
| Phone number formats | Mix of `(555) 123-4567`, `555-123-4567`, `5551234567`, `+15551234567` | No standardization across sources |
| Null vs. empty vs. "N/A" | Some fields have null, some have empty string, some have literal "N/A" or "none" or "n/a" | Every legacy data migration |

### Category 3: Consent & Compliance Problems (surfaces in Modules 4-5)

| Problem | How It Appears | Real-World Parallel |
|---------|---------------|---------------------|
| No consent records | ~49K contacts, zero consent records — learner must build the automation | MCA's explicit consent requirement |
| Contradictory consent signals | A few records have `email_optin=true` in `loyalty.csv` but `email_optin=false` in `ecom_customers.csv` for the same person | Cross-source consent conflict |
| Consent without contact point | Some Individuals get consent records but their Contact Point Email hasn't been created yet | Data stream refresh ordering |

### Category 4: Segmentation Edge Cases (surfaces in Module 9)

| Problem | How It Appears | Real-World Parallel |
|---------|---------------|---------------------|
| Tier boundary cases | Members with exactly 25,000, 50,000, or 75,000 points — old tier or new tier? | Off-by-one in segment filters |
| "Lapsed" ambiguity | Last purchase exactly 180 days ago — does "no purchase in 180 days" include today? | Inclusive vs. exclusive date logic |
| Multi-product purchasers | Customers who bought both SeeClear AND Visionaire — appear in both segments | Segment overlap awareness |

### How Dirty Data Surfaces

The dirt is NOT called out upfront. Learners discover it naturally:

- **Module 6 (Data Ingestion):** CSVs just have the problems in them. When learners ingest and check record counts, numbers won't match expectations.
- **Module 8 (Data Graphs):** Orphaned orders with missing product references cause relationship gaps.
- **Module 7 (IDR):** Identity problems hit hardest here. Cross-source email mismatches, name variations, and duplicate records all surface.
- **Module 9 (Segmentation):** Boundary cases and overlap surface during spot-checks.
- **Module 10 (Consumption):** Dirty data inflates consumption. Learners estimate savings from cleanup.
